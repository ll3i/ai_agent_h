# 디벨롭 적용 인사이트 (V7 → V8 → V10 → 다음 버전)

**평가**: Binary F1-Score · **목표**: Private(100장) F1 상향

| 버전 | 리더보드 F1 | 전략 요약 | 함의 |
|------|-------------|-----------|------|
| V7 | 0.57 | V4 Baseline + Targeted FN (적극 탐지) | Recall↑, FP 많음 |
| **V8** | **0.76** | Cleaned Baseline + Stricter FN (FP 제거·보수적) | **현재 Best** · FN은 증가 |
| V10 | 0.56 | Ultra-Conservative + Edge Specialist | 보수 강화 → FN↑, F1 하락 |

→ **V10(0.56) 인사이트**: 지나치게 보수적으로만 가면 FN이 다시 늘어나 F1이 V8보다 떨어진다. **“FN을 잡되, V8 수준의 과탐(over-kill)은 피한다”**가 다음 목표.

---

## 1. 버전별 전략 요약 (적용 시 참고)

- **V8이 0.76인 이유**:  
  - 알려진 FP 샘플(TEST_004, 013, 026, 036, 057, 063, 094 등) 회피  
  - Orientation/Lead 체크를 “확실한 경우만 DEFECT”로 한정  
  - Empty 체크 유지 → FP 억제에 유리  

- **V10이 0.56인 이유 (가설)**:  
  - Ultra-Conservative로 FP는 줄었지만  
  - 경계 케이스(Twist, Side Lead, Missing Leg 등)에서 DEFECT를 놓쳐 FN 증가  
  - F1 = 2·P·R/(P+R) 이라서, R이 너무 떨어지면 F1이 크게 하락  

- **V11 목표 (코드 주석 기준)**:  
  - “V10/V4가 놓친 ~15개 결함을 잡되, V8만큼 과탐하지 않는다”  
  - → **선택적 공격성**: 리드/자세/빈칸 같은 특정 패턴만 더 세게 보고, 그 외는 V8 수준으로 유지  

---

## 2. 적용할 인사이트 (우선순위)

### 2.1 리드(다리) 결함 — FN 최우선 타깃

**현상**  
- 단일/다중 리드 끊김, Missing Leg 등이 FN의 대부분.  
- TEST_046(옆 연결), 028/055/060(다리 누락) 등이 문서에 반복 등장.

**적용 포인트**  
1. **리드 전용 프롬프트를 한 단계 “스마트하게” 강화**  
   - “SHORT/CUT, MISSING, SIDEWAYS, Floating” 등을 **명시적으로** 열거.  
   - “그림자/접힌 부분/가로지르는 리드는 정상”처럼 **FP 억제 규칙**을 같이 넣기. (현재 V11 LEAD_SPECIALIST에 반영된 방향 유지·강화)  
2. **엣지 케이스 전용 1문장 추가**  
   - “리드가 2개만 보이면 DEFECT”, “옆으로 90° 꺾여 보이면 DEFECT” 등 **짧고 구체적인 문장**을 프롬프트 상단에 두기.  
3. **(가능하면) 리드 개별 검사**  
   - 리드 1/2/3별로 “이 리드만 보여주고 연결 여부만 물어보기” 같은 단순 질문을 추가하면, 리드 끊김 FN을 더 줄일 여지가 있음.

---

### 2.2 Orientation / Twist — 선택적 강화

**현상**  
- TEST_014(45° 비틀림), TEST_020(뒤집힘), TEST_046(옆 연결) 등 회전·자세 FN이 존재.

**적용 포인트**  
1. **“Twist / Flip / Upside-Down”을 한 프롬프트에 같이 명시**  
   - “45° 이상 비틀림 / 다리가 위를 향함 / 동그란 뒷면이 보임” → DEFECT 조건을 **문장으로 구체화**.  
2. **각도/자세를 숫자·상태로 말해 주기**  
   - “0°가 정상, 45° 이상이면 DEFECT”처럼 기준을 적어 두면, V8보다는 조금 더 공격적으로 잡을 수 있음.  
3. **V8 “minor tilt 무시”와의 균형**  
   - “30° 미만 tilt는 NORMAL, 45° 이상 twist는 DEFECT”처럼 **임계를 문장으로 구분**해 두면, V10처럼 과보수만 되지 않게 조절하기 좋음.

---

### 2.3 부품 없음(Empty) — 유지·강화

**현상**  
- TEST_008, 084 등 “아무것도 없음”이 간혹 정상으로 나오는 패턴이 문서에 있음.

**적용 포인트**  
1. **Presence 체크는 최상단·가장 짧게 유지**  
   - “검은 트랜지스터 몸체가 보이면 YES, 보드만 보이면 NO” 수준이면 됨.  
2. **NO면 곧바로 DEFECT**  
   - 추가 판단 없이 1(Abnormal) 반환. 현재 V8/V10/V11 흐름과 동일하게 유지.

---

### 2.4 FP 억제 — V8 수준 유지, “새 FP”만 조심

**현상**  
- V8은 알려진 FP(TEST_004, 013, 026, 036, 057, 063, 094 등)를 줄여 0.76을 기록.

**적용 포인트**  
1. **리드/자세를 강화할 때 “과탐 조건”만 문서화**  
   - “그림자/리드 겹침/살짝 휨 = NORMAL”을 프롬프트에 항상 넣기.  
2. **가능하면 2단계 검증 시험**  
   - 1단: (V11처럼) 스마트 리드·자세 체크로 후보 Abnormal 많이 뽑기.  
   - 2단: “정말 결함인가?”만 묻는 짧은 검증 호출로 확정하고, 애매하면 Abnormal 유지.  
   - 구현 비용이 크면, 우선은 **프롬프트 안에 “오탐 방지 문장”만 강화**해도 효과 있을 수 있음.

---

### 2.5 V10 → 다음 버전으로 가져갈 설계 원칙

1. **“Ultra-Conservative 전체”는 피하기**  
   - V10처럼 모든 체크를 동시에 보수적으로 하면 FN이 늘어나 F1이 떨어짐.  
2. **체크별 민감도 분리**  
   - Empty: 지금처럼 단순·민감 유지.  
   - Lead: **조금 더 공격** (SHORT/MISSING/SIDEWAYS 명시 + FP 방지 문장).  
   - Orientation: **Twist/Flip만 약간 공격**, minor tilt는 유지.  
3. **목표 수치로 잡을 것**  
   - Recall 0.80+ 수준을 목표로 두고,  
   - Precision이 크게 떨어지지 않는 선(예: 0.5 이상)에서 F1이 올라가는지 보고 조절.

---

## 3. 체크리스트 (다음 버전 코딩 시)

- [ ] **리드**  
  - [ ] SHORT/CUT, MISSING, SIDEWAYS, Floating 등 DEFECT 조건 명시  
  - [ ] 그림자/휨/교차 리드는 NORMAL이라고 명시  
  - [ ] (선택) 리드별 1문장 질문 추가  
- [ ] **자세/회전**  
  - [ ] 45° 이상 twist / 뒤집힘 / 다리 위로 → DEFECT 문장 추가  
  - [ ] 30° 미만 tilt는 NORMAL 명시  
- [ ] **Empty**  
  - [ ] 첫 단계 presence, NO면 즉시 Abnormal  
- [ ] **FP**  
  - [ ] 알려진 FP 유형(그림자, 미세 휨 등)을 프롬프트에 “NORMAL” 예시로 명시  
  - [ ] (선택) 2단계 검증으로 “의심 → 확정”만 거치기  
- [ ] **실험**  
  - [ ] 동일 제출 형식으로 리더보드 F1 확인  
  - [ ] 가능하면 프로젝트 GT 100장 기준으로 F1/혼동행렬도 같이 기록

## 4. 한 줄 요약

- **V10이 0.56인 이유**: 지나치게 보수적이라 FN이 다시 늘어남.  
- **다음 스텝**: “리드/자세”는 **선택적으로만** 더 공격적으로 잡고, **Empty는 유지**, **FP는 V8 수준**으로 유지하는 쪽으로 조절하면, V8(0.76)을 넘거나 최소한 V10(0.56)보다는 안정적으로 올라갈 가능성이 큼.
