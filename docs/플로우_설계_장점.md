# 설계한 플로우의 장점

이 문서는 `WORKFLOW_DIAGRAMS.md`에 정의된 Luxia AI Agent 워크플로우 설계의 **장점**을 체계적으로 정리합니다.

---

## 1. 전체 구조적 장점

### 1.1 레이어 분리로 인한 장점

- **역할이 명확히 나뉜 4계층**  
  실행 스크립트 → 통합 Agent → 핵심 Agent 로직 → 공통 컴포넌트 순으로 책임이 분리되어 있어, “어디를 고치면 어떤 동작이 바뀌는지” 파악하기 쉽습니다.

- **진입점이 하나로 정리됨**  
  대회 제출은 `run_full_analysis.py` 등 고정된 스크립트를 통해 이루어지므로, 실제 사용 플로우와 실험/디버깅 플로우를 구분하기 쉽고 재현이 단순합니다.

- **의존성이 위에서 아래로만 흐름**  
  상위 레이어가 하위 컴포넌트(ROI 크롭, API 클라이언트, 설정)를 호출하는 구조라, 로직 수정 시 영향 범위를 좁혀서 개발할 수 있습니다.

### 1.2 모듈화·재사용성

- Vision / Knowledge / Report 등 **Agent 단위로 모듈이 나뉘어 있어**, 일부만 교체하거나 조합을 바꾸기 쉽습니다.
- **Final Omni-Agent**는 “Vision → Knowledge → Report” 순서만 정해 두고, 각 단계 구현체를 바꿔도 플로우 골격은 유지할 수 있습니다.
- ROI 크롭, Saltlux API, 설정 등은 여러 Agent가 함께 쓰므로, **한 번 개선하면 전체 품질에 동시에 반영**됩니다.

---

## 2. Judge–Think–Act–Verify(JTAV) 플로우의 장점

### 2.1 단계별 분리로 얻는 이점

- **Judge(관찰)**  
  이미지에서 “어떤 결함 후보가 보이는지”만 뽑아 내고, 결론은 내지 않습니다.  
  → 나중에 잘못 판단했을 때 “관찰은 맞는데 해석/판단이 틀렸다”처럼 **원인을 단계별로 좁혀서** 분석할 수 있습니다.

- **Think(추론)**  
  관찰 결과를 넣어 결함 개수·심각도·치명 여부·신뢰도를 계산합니다.  
  → **의사결정 근거(추론)**가 구조화되어, “왜 Abnormal로 봤는지”를 로그·리포트에 그대로 쓸 수 있습니다.

- **Act(의사결정)**  
  Think 출력에 따라 label·uncertain 플래그를 정합니다.  
  → **규칙이 명시적**이라(예: has_critical_defect → 1, total_defects 기준 분기) 운영·튜닝 시 조정하기 쉽습니다.

- **Verify(검증)**  
  최종 단계에서 “판단의 타당성·도메인 일치·놓친 결함 가능성”을 다시 점검합니다.  
  → **한 번 더 걸러서** 단순 실수나 논리 꼬임을 줄일 수 있습니다.

### 2.2 재검토 메커니즘의 장점

- **uncertain이면 strict 모드로 한 번 더 Judge–Think–Act**를 돌리도록 설계되어 있어,  
  “한 번에 확신이 없을 때만” 비용을 들여 재검사할 수 있습니다.

- **치명적 결함이 있으면 재검토를 생략**하므로,  
  이미 충분히 위험하다고 판단된 경우에는 불필요한 지연을 만들지 않습니다.

### 2.3 신뢰도 추정의 장점

- 결함 개수·치명 여부에 따라 **VERY_HIGH / HIGH / MEDIUM / LOW**처럼 단계를 두어,  
  나중에 “낮은 신뢰도만 사람 검수” 같은 **2차 필터**를 붙이기 좋습니다.

- Verify 단계에서 **검증 후 신뢰도 보정**을 할 수 있어,  
  재검토를 거친 케이스에 한해 최종 신뢰도를 조금씩 올리는 식으로 활용할 수 있습니다.

## 3. Fusion Agent(3단계 적응형 전략)의 장점

### 3.1 결함 개수별 분기

- **0개 결함** → Sensitive Recheck (FN 방지)  
  “정상이라고 나왔지만, 한 번 더 적극적으로 찾아보자”는 전용 단계가 있어,  
  **놓침(False Negative)을 의도적으로 줄일 수 있습니다.**

- **1개 결함** → Precision Verify (FP 방지)  
  “실제 결함인지, 그림자/노이즈인지”만 집중해 묻는 단계가 있어,  
  **오탐(False Positive)을 줄이면서 Abnormal 판정 품질을 높일 수 있습니다.**

- **2개 이상** → 즉시 Abnormal  
  이미 다수 결함이 나온 경우 추가 호출 없이 바로 결론을 내어,  
  **불필요한 API 비용과 지연을 피할 수 있습니다.**

→ 리더보드에서 “F1을 올리려면 Recall과 Precision의 균형”이 중요했던 점과 잘 맞는 설계입니다.

### 3.2 Triple Vision의 장점

- **Full / Body / Lead** 세 시점을 한 번에 넣어 주므로,  
  - 전체 배치·위치 관계(Full)  
  - 패키지·몸체 상태(Body)  
  - 리드 연결·끊김(Lead)  
  을 **한 번의 판단에서 종합**할 수 있습니다.

- 단일 이미지만 쓸 때 발생하기 쉬운 **“리드는 안 보이는데 몸체만 보고 정상으로 넘김”** 같은 한계를 줄일 수 있습니다.

- **ROI 크롭이 선행**되므로, 모델이 “어디를 봐야 하는지”에 대한 힌트를 받고,  
  같은 토크으로 **중요 영역 해상도를 더 잘 쓰도록** 유도할 수 있습니다.

### 3.3 프롬프트 전략 분리

- **Balanced**  
  기본으로 균형 잡힌 판단을 하게 하고, 5가지 결함 유형을 구조화된 JSON으로 받아  
  이후 단계의 분기(0개 / 1개 / 2개+)를 **같은 규칙으로** 처리할 수 있게 합니다.

- **Sensitive**  
  “불확실하면 TRUE”“의심스러우면 결함”처럼 **Recall 쪽으로 무게**를 두어,  
  제조 현장에서 “놓침보다 오탐이 낫다”는 요구를 플로우 차원에서 반영할 수 있습니다.

- **Precision**  
  “실제 결함 vs 그림자/노이즈”를 구분하라는 **엄격한 검증**만 하므로,  
  Sensitive 단계에서 과하게 잡아 올린 케이스를 **한 번 걸러주는 역할**을 합니다.

---

## 4. Knowledge Agent(RAG)·Report의 장점

### 4.1 RAG 기반 검색

- Vision 결과(**reason 문자열**)를 쿼리로 사용해,  
  **과거 결함 사례·도메인 지식**과 매칭할 수 있습니다.

- **유사도가 높은 사례만** 추려서 컨텍스트로 붙이면,  
  “이번 경우는 case_002(솔더 브리지)와 비슷하다”처럼 **판단 근거를 구체화**할 수 있고,  
  제조/품질 담당자가 이해하기 쉬운 설명을 만들 수 있습니다.

- **similarity > 0.1 등 임계값**으로 “거의 관련 없는 사례”는 제외할 수 있어,  
  노이즈를 줄이면서도 **지식 활용 비용을 제어**할 수 있습니다.

### 4.2 보고서·컨텍스트 강화

- **final_reason = reason + kb_context**처럼,  
  Vision 판단 문장에 “유사 사례 설명”을 이어 붙이는 단순한 방식이라  
  구현과 유지보수가 쉽습니다.

- “발견된 결함 / 심각도 / 원인 / 권장 조치 / 신뢰도” 같은 **템플릿**을 두면,  
  나중에 **감사·분석·리콜 대응**에 그대로 쓰기 좋은 형태로 출력을 고정할 수 있습니다.

---

## 5. 실행·데이터 플로우의 장점

### 5.1 제출 vs 디버깅 출력 분리

- **output.csv**  
  대회 제출용으로 id·label만 내보내므로, 형식이 단순하고 채점 스크립트와 맞추기 쉽습니다.

- **output_detailed.csv**  
  id·label·reason(및 필요 시 기타 필드)을 저장하므로,  
  **어떤 이미지에서 어떤 이유로 0/1이 나왔는지**를 나중에 재분석하기 좋습니다.

### 5.2 데이터 플로우의 일관성

- **이미지 로드 → Base64·ROI 전처리 → Vision → (선택) Knowledge → (선택) Report → 결과 수집 → CSV**  
  순서가 문서에 고정되어 있어,  
  - 새 데이터셋을 넣을 때  
  - API/모델만 바꿀 때  
  - 중간에 로깅/저장을 붙일 때  
  **“어디에 끼워 넣으면 되는지”**가 명확합니다.

### 5.3 Example / Test 모드 분리

- **example_images.csv vs test.csv**처럼 **모드별 입력**을 나누고,  
  예제만 돌리거나(빠른 검증), 테스트 전체만 돌리거나(제출 전 검증) 선택할 수 있어  
  **반복 실험과 최종 실행을 같은 파이프라인으로 관리**할 수 있습니다.

---

## 6. 도메인(제조·불량 검사) 적합성

### 6.1 FN·FP에 대한 의도적 설계

- **Sensitive 단계**로 “정상이라 나온 건 한 번 더 확인”하게 하여  
  **불량품 유출(False Negative)** 리스크를 설계 단에서 줄일 수 있습니다.

- **Precision 단계**로 “의심 결함만 엄격 재검증”하게 하여  
  **불량 아닌 것을 불량으로 오판(False Positive)** 하는 비용을 줄일 수 있습니다.

- 제조 현장에서 흔히 말하는 **“의심스러우면 반드시 한 번 더 본다”**를  
  **플로우에 그대로 녹인 구조**라고 볼 수 있습니다.

### 6.2 결함 유형의 명시

- **component_missing, lead_connectivity_fail, body_broken_severe, posture_bad, rotation_severe** 등  
  검사 대상 결함을 **고정된 집합**으로 두어,  
  - 나중에 “리드 결함만 보강”하는 식으로 **유형별 개선**이 가능하고  
  - 통계·리포트에서 **어떤 결함이 얼마나 나왔는지** 파악하기 쉽습니다.

### 6.3 설명 가능성·추적 가능성

- Judge·Think·Act·Verify 각 단계와, Fusion의 Balanced/Sensitive/Precision 단계가  
  **어떤 입력으로 어떤 출력을 냈는지** 기록하기 좋은 형태로 나뉘어 있어,  
  **“이번 로트에서 왜 이렇게 판정했는지”**를 나중에 설명하고 감사할 때 유리합니다.

---

## 7. 정리: 플로우 설계가 주는 이점 한 줄 요약

| 관점 | 장점 |
|------|------|
| **구조** | 레이어·모듈 분리로 수정 영향 범위가 좁고, 진입점이 명확해 재현·운영이 쉽다. |
| **판단 품질** | JTAV로 관찰–추론–결정–검증이 나뉘어 논리 오류를 줄이고, 재검토로 uncertain 케이스를 한 번 더 본다. |
| **FN/FP 균형** | Fusion의 결함 개수별 분기(Sensitive/Precision)로 Recall과 Precision을 동시에 다룰 수 있다. |
| **시각 정보** | Triple Vision으로 전체·몸체·리드를 같이 보여 주어, 맥락과 디테일을 함께 활용할 수 있다. |
| **도메인 반영** | RAG·보고서로 과거 사례·설명을 붙여, 제조 현장의 “이유 있는 판정·기록” 요구에 맞출 수 있다. |
| **운영** | 제출용/상세 출력·Example/Test 분리로, 대회 제출과 디버깅·실험을 같은 파이프라인으로 안정적으로 돌릴 수 있다. |

위 내용은 `WORKFLOW_DIAGRAMS.md`에 정의된 플로우를 기준으로 정리했습니다.  
실제 구현체가 Omni-Agent / Fusion / JTAV / Triple Vision 중 일부만 쓰더라도, **설계 관점에서 플로우가 가져다 주는 이점**은 위와 같이 요약할 수 있습니다.
